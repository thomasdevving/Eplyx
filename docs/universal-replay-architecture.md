# Universal replay architecture — code map and design gate

Status: design gate. The U3F records remain experimental until the product path reproduces their retained execution evidence. This document does not grant admission to corpus, bundle, or CI.

## Proposed replay unit

`ReplayObservation` is an immutable manifest with `schema_version`, `id`, `protocol`, `genesis_hash`, transaction signature/slot, `ExecutionInput`, `EvidenceReferences`, `RuntimeContext`, `ExpectedHistoricalOutcome`, `SemanticTarget`, dependency roles, and infrastructure-selected `FidelityProfile`. V1 is a separately parsed representation, converted to the same resolved execution request at read time. Conversion retains V1's historical fidelity profile and never asserts evidence that V1 did not capture.

`ExecutionInput` is a tagged enum. `Legacy` holds the original legacy message. `V0` holds the native compiled message and references to historical LUT observations. The V0 resolver rebuilds loaded addresses through `message::reconstruct`, checks the transaction-specific lookup-index proof, and binds the normalized transaction to the resulting key space. Its identity hashes the variant, header, blockhash, static keys, lookup descriptors, compiled instructions and raw instruction bytes, and LUT historical evidence identities. A future message variant should alter message resolution and backend submission, not corpus or fidelity.

`EvidenceStore` is bundle-local immutable CAS. Content objects are SHA-256 addressed and verified on every resolution. `AccountContent` includes owner, lamports, executable, rent epoch and complete data. `AccountObservation` binds address, requested historical boundary, returned context, provider provenance and content hash. Equal content at different slots can share bytes but must have distinct observation identities. Binary evidence binds program ID, loader, ProgramData address, deployment slot, authority when present, ELF hash and historical account observations. Runtime evidence records exact sysvars and the provenance/materiality of feature, SlotHashes, signature, blockhash and Instructions policies separately from ordinary accounts. No stored success flag is authority.

`EvidenceResolver` performs all identity, provenance, boundary, address, dependency, runtime and message-proof checks without network access. It returns a `ResolvedReplayInput`, never an unverified record. `ExecutionBackend::execute` accepts the resolved message, state, dependencies and runtime context and returns complete `ExecutionEvidence`. LiteSVM is the initial implementation. Runtime failures distinguish `UnsupportedRuntimeFeature` from `InsufficientRuntimeEvidence`; neither is a claim that the protocol is unsupported.

`FidelityEngine::compare` receives the historical outcome and local evidence. The infrastructure fixes the profile, independent of adapter choice. V1 checks its recorded outcome, fee, CPI summary and post-state hash. V2 requires exact outcome, fee, logs, grouped CPI outer/program/account indexes, instruction data and stack heights, return-data representation, watched-account presence, owner, lamports, executable, rent epoch and full data. Empty return data is the sole representation normalization. Only a matched result can be passed to semantic interpretation; a missing adapter yields `semantic coverage unavailable` after successful replay.

An envelope role is an infrastructure-level property of each outer instruction: semantic target, target prerequisite, execution dependency or standard companion. A `SemanticTarget` binds the program ID and outer index. Only that target is offered to the adapter. Role labels cannot skip execution or relax fidelity. A record identity hashes protocol, signature/slot, target index, message identity, historical observation identities, dependency set, runtime identity and fidelity profile. It excludes paths, wall clock and random values.

## Revision checks before product admission

The existing `compare_with_dependencies` assumes a single baseline program and returns a report whose `Fixture`/`ExecutionResult` omit watched-account absence and exact CPI. Simply adding an optional v0 field to `ReplayRecord` would retain two incompatible execution and fidelity contracts. The product path needs a common result type and a versioned reader. The U3F example's protocol-specific `envelope::admit` must not become a core execution prerequisite. The new resolver must reproduce its generic LUT, state, binary and runtime checks before the example can be retired.

The architecture remains provider-neutral if only the collector knows an archive vendor. The durable evidence contract stores scheme/host and capability proof without credentials; no resolver branch tests provider name. Another message version should require a new `ExecutionInput` variant and backend support, with no evidence-store, bundle, corpus or semantic schema change. A new loader/runtime profile may add binary and runtime metadata plus backend capability checks, with no adapter changes.

## Product execution contract

The schema-2 product path is `ReplayObservationV2::resolve` → `ExecutionBackend::execute` → `compare_v2` → optional `ProtocolAdapter` interpretation. The old JSON remains `ReplayRecord` under its historical V1 profile, and `replay::execute` now calls the same `LiteSvmBackend` API. The V1 and V2 stores and bundle manifests are versioned; old bundle bytes are not rewritten.

Eplyx owns message proof, account and binary identity, exact-slot provenance, dependency completeness, runtime policy, the watched-account census, baseline fidelity and expectation review. `ExecutionRequest` passes the proven native legacy or v0 message, resolved account seeds, historical sysvars, loading rules and signature/blockhash policy to a backend. LiteSVM owns Solana instruction execution, built-in programs, account mutation, fees, logs, CPI trace and return data. Eplyx reads the backend's results into presence-preserving `ExecutionEvidence` and compares them to validator and archived account evidence. A future backend must implement the same request/result contract; it cannot substitute a different fidelity policy.

For v0, Eplyx re-derives loaded keys from frozen transaction bytes and exact-slot LUT account observations. The executor submits the native `VersionedTransaction`; it never executes a legacy flattening. For upgradeable programs, Eplyx proves the executable header → ProgramData link, loader, deployment slot, authority, full ELF and allocated account bytes before seeding ProgramData ahead of executable accounts. For legacy binaries it checks the loader and exact executable bytes. Historical Clock, Rent and EpochSchedule accounts are separate runtime evidence. SlotHashes is either historical with its own account observation, or the `materiality_checked_default` policy, which demands byte-identical execution across default, empty and differing hashes. Signature and blockhash checks are explicit backend inputs; the current historical V2 profile has them disabled. The Instructions sysvar is constructed by the runtime from the complete compiled message.

`RuntimeContext::capability` has three results: `SupportedByCurrentBackend`, `UnsupportedRuntimeFeature`, and `InsufficientRuntimeEvidence`. The last two are operational limits of the chosen runtime or captured evidence, not assertions that a protocol is unsupported. The current feature profile is explicitly `LiteSVM 0.16.0 mainnet`. A new loader or feature profile would require new binary/runtime evidence rules and a backend capability check; it should not require changes to a protocol's economic adapter.

## Capability matrix

| Case | Replay support | Structural understanding | Semantic support | Production assurance |
| --- | --- | --- | --- | --- |
| Existing Stake Pool bundle | V1 historical profile | V1 outcome, fee, CPI summary and post-state hash | Stake Pool subjects | Existing production pilot |
| Two-record Kamino bundle | V2 complete profile | Exact logs, CPI, return, presence and all watched account bytes | Deposit and borrow subjects | Bounded production-derived interactions; no representativeness claim |
| Unknown protocol with adequate historical evidence | V2 replay does not require an adapter | Complete execution and state evidence | None; CI reports no semantic coverage | Replay-only until economic interpretation is supplied |

The current corpus selector and historical acquisition tooling are not a general collector for arbitrary protocols. The schema-2 resolver and executor are provider-neutral after evidence is captured. Its retained receipt schemas describe exact-slot requests and response hashes; archive vendor names are provenance values, not branches in replay. Another message format can add an `ExecutionInput` variant and backend submission path while reusing account CAS, fidelity, corpus, bundle and semantic APIs. Failed historical transactions need further proof of a canonical error representation before they can satisfy the current V2 equality rule.

The current schema-2 records are native v0. `ExecutionInput::validator_transaction_ref` makes the validator-envelope requirement message-neutral, but the `Legacy` variant used to adapt V1 records has no frozen validator envelope and therefore cannot currently be admitted as a new complete-profile schema-2 record. A future fully evidenced legacy importer must add that reference and prove the raw compiled message against it. This is a bounded message-proof gap, not a reason for another corpus, bundle, fidelity or semantic model.
