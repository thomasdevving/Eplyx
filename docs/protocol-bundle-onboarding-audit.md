# Protocol bundle onboarding audit

Implementation follow-up: the bounded schema-1 recommendation below is implemented
by [`eplyx bundle prepare`](bundle-qualification.md). The audit retains its original
pre-implementation findings; the operator document describes the current contract.

## Decision and scope

The next implementation should be a **bounded operator bundle qualification command for schema-1, already-supported adapter and replay shapes**. It should compose the existing discovery, acquisition, selection, build, and verification paths, and publish an evidence and coverage receipt. It must stop at a missing adapter, unsupported transaction or runtime shape, or absent historical evidence; an unmeasured semantic production population must remain `unknown` and require explicit coverage review. It must not register or activate a project bundle. The contract and acceptance criteria are at the end of this audit; this phase makes no implementation change.

An operator starting with only a program ID and an intended upgrade-analysis scope cannot yet obtain a qualified bundle. They also need a compiled adapter for that exact program and requested actions, a replay topology the engine supports, a chosen production window and corpus budget, transaction/block history, exact historical account and executable evidence, a common historical baseline and dependency set, and an explicit coverage review. Some of those are engineering or provider capabilities; scope, coverage acceptance, and activation are operator decisions.

## Reference pipeline and proof boundary

```text
observed production activity (discovery; structural labels)
  → candidate signatures and exact historical acquisition (may be refused)
  → replay-eligible evidence (boundary, message, executable, dependency and runtime proofs)
  → semantically supported evidence (adapter recognition, roles, evaluable subjects)
  → selected corpus (deterministic policy and stated limitations)
  → V1 fidelity validation (baseline reproduces original outcome)
  → qualified, verified bundle (content-addressed, offline)
  → operator registration and deliberate activation (project baseline)
```

The order is conceptual: the schema-1 selector classifies acquired records before `bundle build` runs baseline fidelity. Thus its output is a **proposed** selection, even though the CLI/help and older Phase 9 wording sometimes call records “validated.” A successful `historical acquire` is not a V1 match; a successful V1 match is not proof of economic meaning; a verified bundle is not an active project baseline. See [`historical.rs`](../engine/src/historical.rs), [`select.rs`](../engine/src/select.rs), [`bundle.rs`](../engine/src/bundle.rs), and [`main.rs`](../engine/src/main.rs).

The script actually runs discovery → up to a configured number of acquisitions → structural and corpus reports → `corpus select` → `bundle build` (which selects again) → `bundle verify`. It chooses the first `*-mainnet-v1.so` filename as baseline and removes its output bundle directory before rebuilding. Its comments and its `Helius`/`Alchemy` examples document one deployment, not provider dependencies. It intentionally does **not** pass structural discovery counts as `--observed`. [`production-pilot.md`](production-pilot.md) records that the production copy stayed byte-identical and that registration left the project in `setup` until explicit activation.

## Four kinds of onboarding work and four meanings of “new protocol”

| Kind | Current responsibility | Safe automation boundary |
| --- | --- | --- |
| **A. Generic deterministic machinery** | Normalization, identity/hash checks, corpus store, deterministic schema-1 selection, baseline fidelity, bundle build/open, server compatibility checks | Compose and report these without changing their predicates |
| **B. Adapter-specific knowledge** | Exact program/shape recognition, ordered roles, account decoding, semantic action, quantities, economic subjects/findings and provenance | Reuse compiled adapters; code review and tests are required for new semantics |
| **C. Historical evidence acquisition** | Finalized tx/block, exact boundary state, ProgramData/ELFs, CPI dependency set, LUTs and runtime/sysvar/feature evidence as needed | Request and retain evidence; fail closed on missing or unsupported proof |
| **D. Human scope/policy** | Action scope, production window, record budget, coverage-gap acceptance, project registration and activation | Record choices explicitly; never infer acceptance from a green replay |

| Case | What is needed now |
| --- | --- |
| **1. Already-supported adapter and execution shape** | The program ID must match a compiled adapter (a different deployment ID is not automatically covered). Supply scope, history/archive/block endpoints, acquire accepted records, select within one V1/dependency cohort, build/verify, review coverage, then register/activate separately. A new project using the same program/bundle may only need administration; a new cohort still needs evidence qualification. |
| **2. Known program, new action/shape** | Extend the adapter's recognition/roles/readers/economic interpretation and tests; update its version if meanings or supported shapes change. Then acquire and qualify records. An unknown semantic action is not made supported by a successful replay. |
| **3. Known semantics, unsupported replay topology** | Add or supply the missing execution/evidence contract first: e.g. exact LUT, account creation, same-slot closure, runtime feature/sysvar or dependency proof. Schema-2 complete/checkpointed replay supports some prepared witnesses, but there is no arbitrary-protocol collector. Adapter code alone does not cure an evidence gap. |
| **4. Entirely new program/protocol** | Build/register a new adapter for its exact ID and intended actions, prove its execution topology and historical evidence, measure coverage, then qualify a bundle. A prepared schema-2 bundle may replay with `none@0`, but CI reports `no_semantic_coverage`; that is not a qualified semantic upgrade gate. |

## Semantic qualification and coverage measurement

Raw execution follows `ReplayObservationV2::resolve` → backend execution → fidelity comparison → optional adapter interpretation; schema 1 keeps its historical V1 fidelity profile. The adapter then must recognize the intended instruction, bind exact account roles and access/type constraints, decode only supported state, classify an action, compute observations/findings and expose an evaluable CI subject. Recognition, role binding, successful replay, source provenance, and economic meaning are separate claims. [`protocol/mod.rs`](../engine/src/protocol/mod.rs) defines the trait and registry. [`phase-u16-minimal-protocol-onboarding-contract.md`](phase-u16-minimal-protocol-onboarding-contract.md) describes the bounded `ProtocolDescriptor`/role contract already used by Orca and Drift; Stake Pool, Kamino and Token-2022 retain their existing paths.

For another action in a known adapter, the minimum is an unambiguous recognizer/instruction contract, exact role/companion checks, necessary account decoders and state links, action classification, deterministic economic quantities/subjects/findings with provenance or explicit unevaluability, tests for accepted and refused shapes and boundary values, and an adapter-version bump whenever interpretation changes. A new program also needs a `ProtocolAdapter` implementation, exact-ID registration in `adapters()`, semantic binding/evaluator where justified, and the same tests plus independent replay/evidence qualification. Shared standard-program/token evidence can reduce decoding work; it does not assign economic meaning. A descriptor is a small entry contract, not automatic semantic support.

Coverage has three denominators with different provenance: **observed production** in a declared transaction window; **acquired/replayable** under exact evidence and then V1 fidelity; **selected** for the gate. Current discovery derives structural/direct/CPI and failure counts; the script cannot convert them to semantic `ObservedCounts`. `select::select` can derive replayable and selected action counts from adapter-classified acquired records and deterministic novelty from entity, pool, amount, boundary, invocation shape and time; its legacy amount/pool extraction has Stake Pool keys, so it should not be advertised as uniformly protocol-neutral. `--observed` is caller supplied, vocabulary-checked, and its provenance/completeness are **not** verified. Missing counts remain unknown. A measured action with zero eligible records produces an explicit limitation; low yield and shortfall also produce limitations. The pilot's four contract limitations cover failed original transactions, account creation, rent behavior and LUTs; they are not a substitute for measured action denominators. A semantic production population requires a separately specified complete window and action-classification method, with unknown/unsupported/failed interactions accounted for. Never put discovery's structural counts into `--observed` or interpret no acquired records as no production use.

## Where the current chain stops, and what can be automated

For case 1, the commands already compose a qualified **schema-1** bundle if the supplied window yields records within the adapter's legacy acquisition contract and the baseline fidelity gate matches. The durable intermediates are discovery JSON/report and corpus records/manifests/binaries. Dependency binary resolution is automatic for the supported path, but the script uses a filename heuristic to choose the baseline, selects twice, does not persist a structured qualification receipt, and does not measure semantic production counts. Operator configuration still decides the scope/window/budget and provider credentials. If acquisition yields no exact boundary, if records span target/dependency versions, if a runtime shape needs schema 2, or if the adapter does not cover the intended action, no sequence of existing commands creates support. Schema-2 bundle build/verify accepts a **complete reviewed, prepared** corpus; `bundle build --target-size` expressly refuses schema-2 selection, and there is no generic discover → acquire schema-2 collector.

Safe orchestration candidates are prerequisite inspection, adapter/version and replay-contract preflight, provider/genesis/archive probe, deterministic candidate queue and per-signature refusal ledger, hash-based V1/dependency cohort grouping, copying exact hashes/IDs between commands, one selection policy invocation, fresh output assembly, build/open verification, and a machine-readable receipt linking source window, acquisition failures, selected IDs, V1 fidelity, limitations and bundle hash. These remove tooling friction. They cannot silently relabel approximations as exact state, synthesize a baseline or runtime profile, infer absent actions from a narrow sample, or manufacture adapter coverage. The existing script is a useful prototype, not a general product contract: it contains Stake Pool assumptions, current shell defaults, and a destructive output refresh.

The operator must still supply credentials and choose program ID, supported action scope, window, budget and production population measurement method. They must review acquisition losses, runtime assumptions, semantic coverage and whether limitations make the pilot worthwhile. Adapter changes require code review and evidence-specific tests. Project target/workspace linkage, bundle registration and deliberate activation belong to the separate administrative pipeline: [`pilot-onboarding.md`](pilot-onboarding.md) and [`phase-10-hosted-ci.md`](phase-10-hosted-ci.md) already separate a verified artifact from the active pointer. A qualification command may print registration inputs, but must not activate merely because build succeeds.

## Proposed operator-facing qualification states

These are evidence states for one declared program/scope/window, not a percentage. A state may carry one or more explicit blockers; later evidence does not erase earlier observed failures.

| State | Established | Not established; next action |
| --- | --- | --- |
| `scope_unqualified` | Program ID and intended scope recorded | No support/evidence claim; check exact adapter/action and replay contract, choose window/providers |
| `support_blocked` | A particular adapter, semantic shape, message topology or runtime capability is missing | No qualified acquisition; implement/review the missing contract or narrow scope explicitly |
| `acquisition_blocked` | Discovery and attempted signatures/refusals are recorded | No exact replay-eligible set; obtain correct historical capability or another window without relaxing evidence |
| `evidence_acquired` | At least one record has accepted historical account/executable inputs and a declared runtime profile | No V1 match or bundle; group by V1/dependencies, measure or mark observed counts unknown, select |
| `bundle_candidate` | Proposed selection and one baseline/dependency cohort are fixed | No qualification until baseline fidelity succeeds; run build and inspect mismatches |
| `bundle_verified` | Every selected record matched V1 at build; bundle was reopened and hashes/identities verified | No administrative baseline or coverage acceptance; review limitations and scope |
| `coverage_review_required` | V1-qualified selected counts and limitations are visible; semantic gaps or unknown observed denominator remain | No claim of adequate scope; operator decides whether to proceed, rescope or seek adapter/measurement work |
| `ready_for_activation` | Verified bundle and explicit operator acceptance of scope/limitations, compatible target project identified | Not active; register and deliberately activate via administrative flow |

`ready_for_activation` is a receipt/review status, not a flag inferred by `bundle verify`. A missing semantic population is recorded as `unknown`; whether that gap permits a bounded pilot is a human policy decision, not a zero. If no selected record is evaluable for the declared CI subject, the state stays `support_blocked`/`coverage_review_required` even when replay and hashes match.

## Bottleneck ranking

| Rank | Cost | Why it dominates or does not |
| ---: | --- | --- |
| 1 | Exact historical state, executable/dependency and runtime/topology qualification | The provider must supply exact boundary evidence; same-slot writes, LUTs, creation, dependency upgrades and runtime features can make a real transaction ineligible. Schema 2 has stronger prepared-witness machinery but no general collector. This can block before semantic work starts. |
| 2 | Semantic adapter and subject qualification | For an entirely new protocol, recognizing roles and proving economic quantities is independent engineering and review work. For a known action it may be small; for new state/math it can dominate. Replay success cannot replace it. |
| 3 | Measured production semantic action population and coverage review | Counts need a meaningful classifier and complete declared window; the current script has structural counts only. Missing denominators make representativeness and action-yield claims impossible. |
| 4 | Deterministic corpus/bundle assembly and operator handoffs | Code largely exists; duplicate selection, filename baseline choice, ID/hash propagation and lack of a receipt create avoidable friction. |
| 5 | Hosted project/target/workspace setup | Separate administrative commands and explicit activation already exist; mostly coordination after a bundle is qualified. |

The ordering changes by case: historical evidence is usually first for an already-supported adapter, while novel protocol semantics may be the largest engineering task in case 4. This is a difficulty ranking, not a time estimate.

## One recommended next implementation: bounded schema-1 qualification orchestrator

Build one operator command (for example, `eplyx bundle prepare`) **only for exact program IDs with compiled adapters and transaction shapes accepted by the existing schema-1 `ProtocolArchiveProvider`**. The choice follows from the working CLI chain and the local pilot funnel: there is enough existing machinery to remove repeated coordination without claiming generic schema-2 acquisition or new semantics. This phase should create a durable receipt and stop with typed blockers, not widen replay admission.

**Inputs.** Program ID; operator-declared action/CI subject scope; slot window; transaction, exact-slot account and block provider configuration/credentials; candidate and bundle budgets; fresh output root; optional externally measured semantic observed-count artifact with its window/classifier provenance. The command must distinguish missing measurement from a measured zero. Provider URLs/credentials are runtime inputs and must not be copied into bundles or receipts; safe provider identity/capability metadata may be retained.

**Outputs.** Immutable discovery report, candidate/attempt/refusal ledger, acquired schema-1 corpus, selected-record and limitation report, one verified bundle when possible, and machine-readable qualification receipt containing program/genesis/adapter version, declared scope/window, provider capability results, V1/dependency cohort hashes, observed-count provenance or `unknown`, acquired/selected counts, per-record fidelity result, bundle hash and current state/blockers. Failed runs still produce a receipt. No server state changes.

**Likely components.** Add a CLI subcommand/orchestrator in [`main.rs`](../engine/src/main.rs), reusing [`discovery.rs`](../engine/src/discovery.rs), [`historical.rs`](../engine/src/historical.rs), [`corpus_store.rs`](../engine/src/corpus_store.rs), [`select.rs`](../engine/src/select.rs), [`bundle.rs`](../engine/src/bundle.rs), [`versions.rs`](../engine/src/versions.rs), [`dependencies.rs`](../engine/src/dependencies.rs) and the adapter registry. Replace the policy parts of [`scripts/acquire-corpus.sh`](../scripts/acquire-corpus.sh) with a thin example or deprecate them after parity. Add focused tests for orchestration/receipt boundaries; do not edit adapters or fidelity predicates as part of this phase.

**Acceptance criteria.**

1. A fixture-backed run for a compiled, supported schema-1 adapter produces a bundle that `bundle verify` opens and a receipt that links every selected ID to its acquisition and V1 fidelity result; baseline/dependency hashes come from records, never a filename heuristic.
2. Re-running with the same frozen inputs gives the same selected IDs, bundle hash and canonical receipt facts; timestamps, URLs and credentials cannot perturb bundle identity.
3. A missing adapter/action/subject, unsupported transaction/CPI/LUT/runtime shape, archive slot mismatch, same-slot conflict, mixed V1 or dependency versions, or V1 mismatch stops with a typed blocker and no `bundle_verified` claim. Refused observed transactions remain counted in the ledger.
4. Structural discovery counts cannot enter `--observed`; absent measured counts are `unknown`, and an externally supplied count artifact must name its semantic classifier, scope and window. A measured action with no replayable record remains an explicit coverage limitation.
5. The command emits `bundle_verified` only after baseline fidelity and bundle reopening pass. It never registers, activates, changes a project target, or suppresses limitations. A receipt may say `ready_for_activation` only after an explicit recorded operator coverage acceptance.
6. A prepared schema-2 corpus is reported as outside this command's acquisition/selection contract, with its existing `bundle build`/`verify` path identified; the orchestrator does not down-convert it to schema 1.

**Non-goals.** New adapters/actions or economic formulas; generalized schema-2 collection or selection; new provider integrations; invented historical runtime or account evidence; an automatic semantic production-action classifier; representative-traffic claims; project/workspace setup, bundle registration, or activation. Those boundaries stay visible in the receipt rather than being filled with guesses.
