# Phase U13.2B — Historical feature-set runtime binding

## Result: U13.2B-A, target-only historical feature execution matches

The generic LiteSVM backend now accepts a content-bound historical feature set and constructs the VM with that set **before** builtins, runtime environments, sysvars, feature accounts, and default programs. With the frozen U13.2A ELF, complete parent-slot seeds, exact Clock/Rent/EpochSchedule, and original v0 message, the Drift transaction at slot **409942000**, index **73**, succeeds locally. Its fee **6,216**, CU **97,801**, and all **11 logs** match the validator metadata. Both safe target outputs, User and PerpMarket, match their complete archived block-final account snapshots, including raw bytes. This is a **historical execution feasibility** match, not a `ReplayObservationV2` or qualified fidelity proof.

The derived tx-73 SpotMarket data SHA-256 is `edceea1f1e0ef731ebb9903d5651c5e1bee47ca219a4b13b306598a729cf8f85`. It equals the retained block-final hash, but four later successful transactions write that account. Equality does not establish that the block-final receipt observes the tx-73 boundary. U13.1's multi-transaction closure remains the separate path to validate this output. No observation, corpus, bundle, CI qualification, or Drift semantics was added.

## Feature universe and evidence

The exact locked dependency is `agave-feature-set 4.2.2` under LiteSVM 0.16.0. Its [frozen source](examples/phase-u9-freeze/runtime-source/agave-feature-set-4.2.2/src/lib.rs) has **285 registered feature IDs** in `FEATURE_NAMES` and three additional declared buffer IDs. The 311-feature U9 later account inventory covered 250 of the registered IDs, so it was not a complete universe; it also contained 61 older/otherwise unregistered account IDs. This phase acquired exact-slot receipts for all **38** missing source declarations without changing U13.2A's frozen responses. Of these 38, 36 were absent and two were present under non-Feature owners (a prefunded System account and a ProgramData buffer). None was an active Feature account. The union of 311 and 38 identities is 349 and covers every ID declared by the backend source. This proves completeness for **this backend implementation's known gates**, not an exhaustive historical validator feature roster.

It derives **275 active Feature accounts, 3 present but inactive Feature accounts, 68 absent identities, and 3 present non-Feature accounts**. The known prefunded empty System-owned ID is excluded from activation. ## Runtime construction and controls

The explicit constructor follows the frozen LiteSVM `into_basic` sequence: `default()` → historical `with_feature_set` → `with_builtins` → base lamports → `with_sysvars` → `with_feature_accounts` → `with_default_programs` → verification defaults, followed by Eplyx's signature/blockhash policy, historical sysvar overrides, account/program seeds, and execution. This workspace does not enable LiteSVM's optional `precompiles` Cargo feature. A behavioral test reads the runtime-visible Rent sysvar: an empty historical set constructed from `default()` yields 3,480 lamports per byte and threshold 2, while `new().with_feature_set(empty)` retains the later 6,960-byte-rate Rent image. The backend uses the tested constructor function.

Nine feature mutations fail closed: an omitted active gate; false activation of inactive and absent gates; altered owner; altered activation slot; removed raw source; changed inventory identity; changed feature-set hash; and a post-target default feature enabled. Owner and activation tests recompute the changed raw response hashes and inventory IDs; every test also recomputes the enclosing runtime-evidence ID. They fail because the claimed active set contradicts the retained response-derived state, rather than only because a CAS filename changed. The source responses remain provider observations, not cryptographic validator attestations.

The [feasibility receipt](examples/phase-u13-2b-feature-universe/feasibility.json) retains complete logs, envelope, safe-output comparisons, and counterfactual fingerprints. The exact historical set, current LiteSVM mainnet default, and target set plus the **26 known post-target activations** all produced identical success, fee, CU, logs, return bytes, and three watched account images in this witness. The latter two are diagnostics; the 26-feature variant uses an explicitly labeled backend diagnostic override and cannot become evidence-bound historical output. These equalities do not authorize later features at the target slot.

SlotHashes backend-default, empty, and deterministic-different variants were equal over the complete collected `ExecutionEvidence`. RecentBlockhashes backend-default, empty, and deterministic-different variants were likewise equal; these use `set_sysvar` and therefore change the VM's sysvar state. A different environment blockhash also left the complete execution evidence unchanged. These are bounded materiality findings for this ordinary-blockhash transaction; the archive still does not provide exact historical SlotHashes or RecentBlockhashes bytes.
