## 5. Minimal generic contract to validate when live events exist

No new evidence type was implemented: U6 required the live event shape and completeness behavior to be understood **before** changing schema. The existing `AccountContent` CAS, `AccountObservation`, `AccountSeed`, and `WatchedAccount` are in `engine/src/universal`; the current `AccountBoundary` permits only before-transaction via S-1 and end-of-execution-slot via S. A future generic extension can preserve content deduplication by adding immutable, content-addressed **write observations** and a **timeline proof** rather than embedding account bytes in a record:

1. Bind each raw account event to provider-neutral slot, address, write version, optional signature, full-content reference, raw-event hash, provider provenance, and a qualified finalized-stream receipt. Missing transaction attribution for a relevant update fails closed.
2. Bind the timeline to a frozen validator block hash, parent, genesis, complete ordered signature/index map, S-1 observed account content, all relevant writes in S, and independently observed end-of-S content. The collector must prove complete delivery, no coalescing of relevant writes, and a resolved finalization/fork choice. End-of-S equality alone cannot reveal a missing transient write.
3. Resolve pre-state from the latest attributed earlier write or observed S-1; resolve post-state from the **final proven target-attributed write** or pre-state when the target did not write. Reconcile every account's terminal content with the independent S checkpoint, including presence, owner, lamports, executable, rent epoch, and full data.
4. Distinguish `ObservedTransactionBoundary` from `DerivedTransactionBoundary`. A derived boundary carries the complete proof path; neither is accepted from a stored Boolean. The observation identity binds slot, signature, transaction index, write versions, content references, raw-event hashes, block identity, checkpoint references, and provenance. `ReplayObservationV2::identity` already hashes its referenced fields, so making boundary references explicit would propagate changes into record and bundle identities. No provider name belongs in the resolver.

This is a **design contract**, not an admitted schema. A real stream must settle whether multiple target-attributed updates can occur and how to identify the final transaction-visible state. A final checkpoint and block transaction index do not by themselves settle delivery completeness, execution order under parallel scheduling, or provider-specific event coalescing.

## 6. Fallback: checkpointed segment replay feasibility

The [bounded block calculation](examples/phase-u6-freeze/segment-feasibility-counts.json) uses the retained accounts-mode block only as a conservative key/writable graph. Direct overlap with the 22 target keys is **0 earlier** and **8 later**. Replaying the full block from observed S-1 through observed S would require **1,131 transactions**: 259 before the target, the target, and 871 after. The block contains 839 legacy, 234 V0, and 58 version-1 transactions, plus 134 failed original outcomes. The exact full transaction envelopes are retained in the U5 full-block response, but historical LUTs, every era-correct binary, full account inputs, runtime data, and canonical failed-transaction comparison are not.

A conservative reverse dependency closure from the target keys through the suffix selects **158 later transactions** and expands the needed target-boundary keyset to **1,217 accounts**. Closing that set through the prefix selects **7 earlier transactions** and requires **1,251 slot-start accounts**: **166 transactions including the target**. That slice contains **23 legacy, 117 V0, 26 version-1** transactions and **81 failed originals**. It is an upper-bound static *candidate*, not an executable proof or a measured minimum; writable flags may overstate actual writes, and an omitted dependency would invalidate the result. Even this slice exceeds U4's native legacy/V0 promise and its successful-transaction CompleteExecutionV2 equality rule. The missing S-1 and S archive checkpoints remain decisive for either full replay or a slice.

A sound slice would need a proven dependency closure over every executable message key, fee payer, CPI-accessible account, LUT, program binary, sysvar, feature, and runtime effect for each included transaction. It must reproduce and reconcile every original outcome, including canonical errors, before using the derived intermediate state, and independently match a later observed checkpoint. A full ordered prefix/suffix avoids the slice omission problem but increases execution and evidence cost sharply. **No segment replay was implemented or run.** Current evidence does not qualify for U6-D (`checkpointed replay feasible`); it supports only a research path.

A retrospective source is needed for old transactions and coverage gaps. Deterministic segment replay remains a recovery route after V1, failed-outcome, runtime, and checkpoint proof requirements are solved. Do not build the service or relax fidelity in U6.
