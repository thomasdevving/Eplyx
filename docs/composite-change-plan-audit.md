# Composite change plan audit (MAIN, 2026-09-29)

## Decision

**Choose one first composition:** two distinct, eligible token-migration units under **one** existing `TokenMigration` ChangeSpec, executed as separate transactions in an explicitly chosen order against one fixed rehearsal bank. Compare `A → B` with `B → A` and with each unit alone. The narrow proof target is shared reserve consumption: each unit can succeed alone, while their combined demand exceeds the same reserve, so order can change which holder migrates. This is an ordered analysis of two operation instances, **not** two different proposals or an atomic transaction.

This is an architecture/product audit. No plan model or implementation is added here. The first implementation should extend migration's existing planner/rehearsal and add one reproducible, content-addressed **migration order case** artifact. It does **not** need a generic persisted `ChangePlan` type. A later cross-kind product may need one, after a real cross-kind handoff contract exists.

The code inspected includes [ChangeSpec](../engine/src/change.rs), [upgrade replay](../engine/src/replay.rs), [universal execution](../engine/src/universal/execution.rs), [candidate seeding](../engine/src/universal/pipeline.rs), [historical sequence](../engine/src/universal/sequence.rs), [migration world](../engine/src/migration/world.rs), [planner](../engine/src/migration/planner.rs), [execution](../engine/src/migration/execute.rs), [rehearsal](../engine/src/migration/rehearsal.rs), [pipeline](../engine/src/migration/pipeline.rs), [current migration](../engine/src/migration/current.rs), [lifecycle consequence](../engine/src/lifecycle/consequence.rs), [path probes](../engine/src/path/mod.rs), [hosted registry](../server/src/registry.rs), and [storage](../server/src/storage.rs). All references describe current code, not proposed behavior.

## 1. Existing identities, inputs and meanings

`ChangeSpec` schema 1 has exactly three kinds: `program_upgrade`, `token_migration`, and `lifecycle_change`. Its ID is SHA-256 over the canonical JSON tuple `(eplyx-change-spec-v1, schema_version, change, activation)`. Label and source metadata, analytical inputs, run ID, bundle, and observed state are outside this proposal identity. A file's stated ID is recomputed on read. The upgrade names target Program and optional ProgramData, candidate SHA-256/length, optional replaced executable and authority expectations, and optional identifying delivery. Squads delivery identifies its exact stored message/proposal; mutable votes/status are observations. Migration names source/destination mints and token programs, conversion, eligibility, burn/escrow, reserve/mint funding, authorities, deadline and exact mechanism program/ELF. Lifecycle names declared asset, successor/terms where known, policy status, sources and effective time. [ChangeSpec](../engine/src/change.rs), [migration spec](../engine/src/migration/spec.rs), [lifecycle spec](../engine/src/lifecycle/spec.rs).

An upgrade ChangeSpec is a proposed executable replacement; replay compares a candidate execution with a baseline execution. It does not execute a loader upgrade transaction. A migration ChangeSpec declares an executable mechanism and economics; its planner builds concrete per-holder transactions in a captured or synthetic world. A lifecycle ChangeSpec declares policy consequences over the **same** immutable snapshot; it does not transfer assets or edit accounts. Current-state transfer/market probes and path scenarios are separate request/fixture identities, not additional `ChangeSpec` variants. `expected-changes.toml` declares acceptable analytical differences for the CI gate; it is run input pinned by hash, not a state transition or part of ChangeSpec identity. [CI review](../engine/src/ci.rs), [path probe](../engine/src/path/mod.rs), [registry](../server/src/registry.rs).

`Activation` may name slot and/or Unix time generically. Migration validation narrows this to exactly one nonnegative axis and its window is inclusive at activation, exclusive at deadline. Lifecycle requires a Unix effective time. Upgrade CI replays historical transactions counterfactually and does not gate on activation. Candidate bytes are resolved and hash-checked separately from specs; a filename is never candidate identity. A run binds the exact ChangeSpec, bundle/state/candidate and analytical records; its verdict remains independent of governance. [ChangeSpec](../engine/src/change.rs), [migration spec](../engine/src/migration/spec.rs), [migration planner](../engine/src/migration/planner.rs).

## 3. Sequence machinery already present

Migration `MigrationPlan` is versioned and hashable, keyed to ChangeSpec, candidate and world hashes. It enumerates units and assigns reserve funding order. Its planner marks a unit `InsufficientReserve` if earlier successful units leave too little; such a unit remains **attempted**, allowing the VM to show rejection and rollback. `rehearse` creates one `Bank`/`Session`, executes attempted units in plan order, then reconciles source supply, destination release/mint, fees and remaining reserve. `Session` keeps the LiteSVM instance and can read accounts between transactions. This is real evolving state, but its overlays, SPL/Token-2022 decoders, authority resolution, reserve arithmetic, candidate ABI and unit instruction builders are migration-specific. The generic part is VM account persistence and execution; `UnitExecution` is not a generic world export. [Planner](../engine/src/migration/planner.rs), [execution](../engine/src/migration/execute.rs), [rehearsal](../engine/src/migration/rehearsal.rs).

Separately, universal historical `sequence` reconstructs a **past** causal transaction closure from a full block and checkpoints, with account dependency edges and a frontier. `LiteSvmBackend::execute_sequence` runs those messages in one VM and compares reconstructed balances/state with observed evidence. It is valuable account-frontier machinery, but its historical block, last-writer, checkpoint, runtime and fidelity contracts do not turn it into a hypothetical cross-kind plan. Other `Plan` types in migration, lifecycle rollout/coverage, and cloud commands are kind-specific intents or workflow arrangements, not an existing generic ordered ChangeSpec plan. [Historical sequence](../engine/src/universal/sequence.rs), [universal execution](../engine/src/universal/execution.rs).

## 4. State handoff and upgrade limits

A sound handoff must carry a bounded, closed account census: exact bytes, lamports, owner, executable flag, rent epoch and **known absence** for created/closed addresses; executable and dependency identities; runtime sysvars/feature set, slot/Clock and blockhash assumptions; authority/signer assumptions; plus the operation's own semantic state (migration reserve, mint supply, token balances). State produced by the VM must be labeled as simulated output. Any B input outside A's output closure must come from a separately pinned initial state or explicit assumption. An unknown account must not be silently filled from a later live RPC read. Hashes alone are insufficient to rerun B: the intermediate account bytes or a verified parent plus exact writes and deletions must be retained.

Upgrade replay already loads candidate bytes: legacy replay registers `LoadedProgram` per independent execution; schema-2 `candidate_seeds` edits target ProgramData/legacy loader account bytes for one resolved transaction. The backend returns watched `post_accounts`, including `None` for absence, but creates a new LiteSVM per ordinary execution. Candidate seeding checks allocation size and does not run loader `Upgrade`, alter authority/deploy slot, or establish a persistent post-upgrade Program/ProgramData world. Dependency binaries and runtime sysvars are resolved for each historical input. Therefore **program upgrade → another supported action is not yet a sound cross-step handoff**. A first-class installed-executable state contract would have to specify loader account/header/capacity, program cache replacement, complete account closure, preserved dependencies/sysvars and compatible fixed time; the existing report does not supply it. The current CI already asks whether each **independent** historical interaction changes under candidate bytes. [Replay](../engine/src/replay.rs), [candidate seeding](../engine/src/universal/pipeline.rs), [universal execution](../engine/src/universal/execution.rs).

Upgrade → migration is meaningful as a future question only if the upgraded target is the migration mechanism or a dependency and the migration world can prove a coherent executable replacement. Present migration `programs()` requires the candidate mechanism ID to be absent from its input world, then inserts the candidate ELF; the world independently supplies token/ATA dependency programs and mint/authority/reserve state. It cannot consume a replay report as `state.json` or infer that an upgrade changed token balances or authorities. An upgrade's Squads delivery match is proposal evidence, not installed-world evidence. Cross-engine conversion is unsupported today. [Migration execution](../engine/src/migration/execute.rs), [migration world](../engine/src/migration/world.rs), [governance audit](governance-review-trail-audit.md).

## 5. Four different ordering claims and time

| Concept | Meaning here | First-phase disposition |
| --- | --- | --- |
| Independent analyses | A and B each start from their own pinned state; `A passes` and `B passes` say nothing about `A → B` | Existing run behavior; retain as comparison/control |
| Ordered analysis | B consumes the simulated result of A; order and intermediate state are evidence | **Selected**, for two migration units in one fixed bank |
| Atomic transaction sequence | Several actions must succeed or roll back as one intended atomic transaction | Not what migration rehearsal does; each unit is a separate transaction and a rejected unit rolls back its own writes |
| Lifecycle/policy timeline | Declared rules are evaluated at different times over an otherwise unchanged snapshot | Keep separate; time change is not an account mutation |

The first order case uses **one fixed captured or fixture Clock** and one runtime profile for both transactions; no time advancement. It requires both units' window to be open at that Clock. An observed world may combine finalized reads from a slot range, so it remains a bounded approximation, not a validator bank. Migration's existing `Activation` rehearsal-clock policy can move the Clock while leaving account bytes unchanged; for this proof use the captured fixed Clock (or a fixture Clock) and refuse a future-only window instead of claiming future state. Historical observation slot, runtime execution Clock, policy effective time and host recording time are distinct coordinates. [Migration world](../engine/src/migration/world.rs), [planner](../engine/src/migration/planner.rs), [lifecycle consequence](../engine/src/lifecycle/consequence.rs).

## 6. Selected two-step composition: exact semantics

**Input.** One validated migration package and its unchanged ChangeSpec ID; exact candidate mechanism ELF; one validated `World` (captured with provenance/completeness or synthetic fixture); candidate/token/ATA program binaries; planner/adapter version; one fixed Clock; two distinct source-account units A and B with available authority paths and individually executable economics. Use **reserve-transfer** funding with one shared reserve. The reserve is either an observed captured account or an explicitly labeled proposed/synthetic vault. To demonstrate the ordering case, each quoted output must fit the initial reserve, while their sum exceeds it. Eligibility must be checked independently of the package planner's population-wide funding order, because that planner may mark either unit `InsufficientReserve` due to other holders.

**Step 1.** Reuse migration's `unit_instructions`, `Session::execute` and `execute_unit`/reconciliation for unit A against a freshly built bank. This is the exact existing supported migration operation, with the same ChangeSpec ID and A's unit ID. Capture pre/post of the bounded account closure and verified rollback if rejected.

**Handoff.** Keep the **same** `Session` VM, unchanged fixed Clock and program set. B reads A's actual post-transaction account state: shared reserve, destination/source token accounts, mint supply, fee payer, escrow/ATA accounts as applicable, including creations or closures. Record a canonical intermediate census/digest of the union of accounts either transaction can read/write plus dependency/runtime identities and absence proofs. Derive it from the VM, not from planner-expected deltas. If any B input is outside that closure or initial world evidence, fail closed.

**Step 2.** Execute B as a separate transaction in that session, reconcile against **current** pre-state. A first-step rejection may leave token state unchanged but still has its own transaction outcome/fee semantics; do not call the pair atomic. Rerun from the same initial bank for `B → A`. Run A alone and B alone from the same initial bank as controls. No result from one permutation is fed into another.

**Output.** Report each ordered step's existing `UnitExecution` outcome, error/failure signature, exact account and reserve deltas, reconciliation, pre/post state identities, plus pair-level ordering-specific difference. In the bounded reserve example, one ordering migrates A and rejects B; the reverse migrates B and rejects A, while both solo controls migrate. This proves a local ordering effect under the pinned world/candidate/Clock and stated signer assumptions. It does not prove production execution, full population readiness, fairness, issuer permission, or future reserve balance. If the concrete candidate behaves differently from the planner, report observed behavior and reconciliation mismatch; never manufacture the example's expected result.

**Unsupported conditions.** Missing or ambiguous account/absence evidence, unknown authority, incompatible program/adapter, changed Clock/runtime, insufficiently closed account set, non-reserve funding for this first case, duplicate unit, ineligible or non-executable unit, candidate/world identity mismatch, unexpected writes outside the closure, or missing reproducible intermediate bytes. A failed transaction is a **supported negative step result** when its rollback is established; it is not automatically an unsupported composition.

Both steps intentionally name the **same** ChangeSpec ID. The distinct unit IDs, ordered positions and transaction messages identify operation instances. This narrower choice preserves proposal identity honestly; calling them two different ChangeSpecs would invent a second proposal. A future genuine two-ChangeSpec plan can reuse the idea of ordered step references without reinterpreting this case.

## 7. Identity, evidence and failure vocabulary

The narrow order-case ID should hash a versioned canonical body containing: migration ChangeSpec ID, exact ordered `(unit_id, source_account, amount)` entries, initial `World` digest and provenance class, candidate SHA/length, existing `MigrationPlan`/adapter identity, fixed Clock/runtime/dependency identities, selected reserve identity/amount and explicit **same-bank, sequential transactions, no time advance** handoff rule. `A → B` and `B → A` therefore have different IDs. Label, prose and display names stay outside identity. The existing ChangeSpec ID remains the proposal identity; the order-case ID is an **analysis input identity**, and a run ID remains an execution occurrence. A paired comparison can refer to both order-case IDs and solo-control IDs without hiding either step.

For a later genuine cross-ChangeSpec plan, `steps: [ChangeSpecId...]` alone is inadequate: the same spec may have multiple operation instances, and the list says nothing about selected inputs, the state handoff, starting-world evidence or timing. An ordered step reference would need at least the step ChangeSpec ID, exact operation/input identity, predecessor-output binding, fixed or advancing-time rule, and explicit assumptions. Reordering must change the plan ID. That future identity should not incorporate display metadata or replace individual ChangeSpec, run, candidate or governance IDs.

Retain after every step: step index and ChangeSpec/unit IDs; input and output state digests; byte-bearing account snapshot or parent-plus-writes/deletions for the complete bounded closure; exact message/instructions, candidate and dependency digests, Clock/runtime and authority assumptions; per-unit `UnitExecution`, reconciliation/rollback, unexpected changes and limitations. `UnitExecution` currently retains changed account **addresses** and a pre-state hash, not a replayable full intermediate world. A new companion evidence artifact is required; a prose summary or post-state digest alone will not do. Reproduction should revalidate initial world/candidate and execute the exact order offline, comparing both intermediate and final evidence; existing migration replay/counterexample bindings offer a pattern, but no new search is required. [Execution](../engine/src/migration/execute.rs), [local reproduction](../engine/src/local_store.rs), [migration pipeline](../engine/src/migration/pipeline.rs).

Keep these results distinct:

| Result | Meaning and suggested representation |
| --- | --- |
| Step analytical failure | Transaction executed and rejected, or executed but reconciliation mismatched; retain existing `Rejected` / `ReconciliationMismatch`, failure signature and rollback |
| Handoff failure | A ran, but B's required input cannot be reconstructed/verified from A plus the pinned initial closure; explicit handoff error, no B verdict |
| Unsupported composition | The pair is outside the reserve-funded, same-spec, fixed-bank contract; explicit unsupported status, not a generic analytical BLOCK |
| Evidence gap | Required captured account, absence, executable, authority, Clock or provenance is missing; explicit indeterminate/evidence-gap status |
| Ordering-specific regression | Solo controls succeed but one order changes a unit's outcome or reconciled economics; derived pair finding naming the affected unit and exact difference |

An ordinary negative migration finding and the pair finding must not overwrite each other. CI's PASS/BLOCK vocabulary remains attached to its own analytical gate; a plan must not infer `A → B passes` from two independent PASS results. [Migration outcome](../engine/src/migration/execute.rs), [migration report](../engine/src/migration/report.rs), [CI review](../engine/src/ci.rs).

## 8. Why other shapes wait

Program upgrade → user interaction is already approximated **independently per replay** by loading candidate bytes before the interaction. It lacks a persisted installed-program world and would need a new replacement/handoff contract before making a stronger ordered claim. Program upgrade → migration additionally needs cross-engine world conversion, mechanism/dependency identity alignment and reserve/authority coherence. Two different migration ChangeSpecs would need replanning the second against the first's output, possibly different overlays/program IDs/population eligibility and an explicit conversion between their worlds. These introduce more semantics than the selected same-spec pair. Lifecycle is a **policy/timeline annotation** or separate consequence analysis, not an executable account-writing step. Current-state path probes also lack a ChangeSpec and reusable post-world contract. [Replay](../engine/src/replay.rs), [migration execution](../engine/src/migration/execute.rs), [lifecycle consequence](../engine/src/lifecycle/consequence.rs), [path](../engine/src/path/mod.rs).

Authority expectations already appear in migration mint and signer paths; G1/G2 governance verifies delivery and deployment evidence for a bound **upgrade** ChangeSpec. Neither offers a generic authority-transfer instruction or state transition. Making permission transfer its own ChangeSpec kind would require a supported transaction shape, source/target authority semantics, account evidence and post-state verification. It is a future kind, not a first plan step. [Migration spec](../engine/src/migration/spec.rs), [governance](../engine/src/governance/mod.rs).

## 9. Runs, storage, governance and review surface

The hosted registry already has per-project run indexes by ChangeSpec ID, immutable candidate objects under `artifacts/programs/<sha256>`, run-local pinned inputs/reports and an object-like filesystem store. The first order case could be a run artifact plus a project-scoped marker from its **order-case ID** to run ID and unchanged migration ChangeSpec ID; byte-bearing initial/intermediate/final evidence should be content-addressed and verified on read. This needs a small index/artifact addition, not a database redesign. Existing individual run/report formats and ChangeSpec IDs remain reviewable. If a later plan has different step specs, its index would list ordered step ChangeSpec/run IDs separately from the plan ID. [Registry](../server/src/registry.rs), [storage](../server/src/storage.rs), [artifact store](../server/src/artifacts.rs).

Governance stays attached to individual ChangeSpec identities. Today Squads G1/G2 is limited to a program-upgrade proposal; this migration order case has no implied proposal, signature, execution or deployment status. A future plan could link separate step governance records or a single proposal only after an exact proposal-to-steps proof exists. Its order identity must never replace a step's governance binding. A review view could present `step 1 input → result → output`, a labeled simulated state handoff, then `step 2`, with independent analytical and evidence statuses. This audit designs no UI. [Governance audit](governance-review-trail-audit.md), [registry](../server/src/registry.rs).

## 10. Technical bottleneck ranking for this first shape

1. **State normalization and identity**: export a complete, replayable bounded account closure from a live `Session`, including absence, after each transaction. This dominates because current per-unit evidence does not serialize that world.
2. **Persistent VM/world state**: already exists within `Session`, but the pair/controls need safe fresh-bank resets and closure checks.
3. **Reporting**: distinguish solo controls, both orders, step rejection, reconciliation and ordering-specific effect without turning all negatives into BLOCK.
4. **Persistence**: store and verify the order-case identity and intermediate evidence beside existing runs.
5. **Timing**: straightforward fixed Clock, but validate window and forbid implicit advancement.
6. **Frontend**: a step/handoff display is straightforward once evidence is sound.
7. **Executable replacement**: unused for this shape; dominant for a later upgrade-first plan.
8. **Cross-engine state conversion**: unused for this shape; likely the largest obstacle to a later upgrade → migration plan.

This ranking is for the selected implementation; it is not a general difficulty ranking for every future composite plan.

## 11. Exactly one next implementation and acceptance

Implement a **bounded migration order case** in the existing migration planner/rehearsal path: select two distinct reserve-funded units under one validated ChangeSpec and pinned world; execute A alone, B alone, A → B and B → A in fresh banks; carry real VM state only between transactions within an order; serialize and verify the initial/intermediate/final account closure; produce two order-case IDs and one comparison report referencing existing `UnitExecution` records. Likely touched components: `engine/src/migration/{planner,execute,rehearsal,pipeline,report}.rs`, a narrow order-case module/artifact in `engine/src/migration`, local replay verification, and only the minimal hosted run/artifact/index code in `server/src/{registry,storage}.rs` if productized there. Keep the existing single-change reports and governance records intact.

The pair must calculate funding expectations **for each chosen order** from the same initial reserve. The population planner's original `InsufficientReserve` classification is tied to its own full-population order and cannot be reused as the expected outcome of a reversed pair. Use its unit quote, eligibility, instruction builder and reconciliation, while recomputing the pair's expected remaining reserve and checking actual VM results.

Acceptance criteria:

1. The same package, world, candidate and fixed Clock reproduce byte-identical order-case evidence offline; changing order changes the order-case ID but never the ChangeSpec ID.
2. A fixture with two individually successful units and a shared reserve smaller than their summed outputs shows an observed order-dependent winner, with exact reserve/balance/mint evidence after **each** transaction. An observed reserve case retains its composite-capture limitations.
3. Solo controls, both orders and per-step reconciliation remain separate. A rejected transaction proves its rollback; a reconciliation mismatch or unexpected write remains visible and cannot be classified as successful migration.
4. Missing input account/absence proof, authority, executable, runtime/Clock, complete closure or intermediate bytes fails closed with an evidence/handoff/unsupported result as appropriate; no live RPC fills the gap during offline replay.
5. Tests cover A → B versus B → A, sufficient-reserve no-difference control, rejected-unit rollback, created destination account and known absence, fixed Clock/window, changed candidate/world/order identity, tampered intermediate bytes, and reproduction from saved artifacts.
6. Individual migration ChangeSpec, candidate and run identities remain independently inspectable; no governance status or overall deployment conclusion is inferred.

**Non-goals:** generic workflow engine or `ChangePlanV2`; two different ChangeSpecs; upgrade installation or cross-engine world conversion; lifecycle account writes; authority transfer; arbitrary time travel; atomic all-or-nothing execution; new search; proposal signing/execution; automatic monitoring; a real-mainnet outcome claim from fixtures. Stop after this bounded two-unit handoff and ordering proof exists.
