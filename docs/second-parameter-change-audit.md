## Decision and scope

Select exactly one next operation: `spl_stake_pool_sol_deposit_fee_v1`. It compares one retained `DepositSol` against the observed pool account and against a pool account produced by executing the deployed Stake Pool program's `SetFee(SolDeposit(Fee))` instruction in an isolated VM. It is a **simulated configuration instruction**, not the direct state derivation used by Step 8. The manager signer is assumed only in that isolated simulation; the analysis does not establish key possession, authorization in a live transaction, governance approval, or an on-chain fee change.

This selection is an implementation contract, not a claim that the VM/config proof has already passed. The first qualification gate must execute `SetFee` against a retained real pool account, verify the resulting account, then replay the existing `DepositSol` with the same deployed ELF. If that gate fails, this operation must fail closed rather than silently fall back to byte patching. This is the smallest honest cross-protocol contract available in MAIN. No parameter is implemented by this audit.

## Step 8 architecture: what can be reused

`engine/src/change.rs` gives schema-1 `protocol_parameter_change` its own `Change`/`ChangeKind`, configuration target, bound operation and stable ChangeSpec identity. The outer shape, mandatory current expectation concept, no activation field, run binding, local `.eplyx` metadata, report sealing, reader verification, offline reproduction command and hosted job kind are reusable. `engine/src/parameter_change/mod.rs` establishes four separate origins: observed account/capture; validated declaration; produced proposed pre-state; simulated downstream post-state. Engine and hosted tamper tests in `engine/tests/parameter_change.rs` and `server/tests/hosted_parameter.rs` establish the first operation's integrity boundary.

The current `Operation` enum has one variant; `ExpectedCurrent`, `Input`, `mutate`, `prepare`, `side`, `consequences`, `finish`, `verify` and `runtime` are specific to an active Token-2022 newer fee schedule and `TransferChecked`. The official in-place mint TLV helper, four-account transfer fixture, current-path capture conversion in `engine/src/path/current.rs`, raw public/withheld token projection, fee findings and guided eligibility/form cannot be reused as Stake Pool semantics. The report's outer binding/status/seal can be retained, but `derived_proposed_pre_state`, `observed_current_state`, `proposed_declaration`, `baseline` and `proposed` need operation-specific payloads; mint- and transfer-named fields must not carry pool data. `server/src/hosted/parameter.rs::validate_parent` currently *requires* a retained current transfer parent and the worker converts that capture with `current::parameter_input`; these are concrete hosted extension points, not already generic input support. Current dashboard/hosted readers call the Token-2022-specific `parameter_change::verify`; dispatch by operation must precede accepting the second report. The guided UI stays out of scope.

## Stake Pool fee scrutiny

MAIN's `StakePool::decode` (`engine/src/protocol/stake_pool.rs`) is a partial sequential Borsh reader. It knows the initialized account tag, the ordering and variable lengths of three `Option<Pubkey>` and three `FutureEpoch<Fee>` values, and reads the active deposit/withdrawal rates. It skips manager, other fees and future-fee values; it ignores trailing fixed-account bytes. It cannot reconstruct an account without losing information. `Fee` is an exact rational with Borsh field order **denominator then numerator**, not basis points. The code's `basis_points` display projection is lossy and must not enter ChangeSpec identity. The official `spl-stake-pool` `StakePool` type derives Borsh deserialize/serialize, while `SetFee` uses that type and serializes into the original account; MAIN currently has no direct `spl-stake-pool` dependency. An official crate version must be pinned against the retained deployed ELF/layout before relying on it for A. The latest published interface documents the fields and serializer, but its version alone does not prove equivalence to the historical ELF. [Official `StakePool` state](https://docs.rs/spl-stake-pool/latest/src/spl_stake_pool/state.rs.html), [official `SetFee` instruction](https://docs.rs/spl-stake-pool/latest/src/spl_stake_pool/instruction.rs.html).

The real `SetFee` takes writable pool and **manager signer** accounts. The processor checks pool owner/validity, checks manager identity/signature, validates the fee and writes Borsh state. For `SolDeposit`, it updates the active `sol_deposit_fee` immediately; for `SolWithdrawal`, it writes `next_sol_withdrawal_fee = FutureEpoch::Two(...)`. Withdrawal/epoch fee changes require an up-to-date pool and withdrawal increases have extra limits. A zero denominator is a valid zero-fee representation in the official fee calculation; a proposed rational must retain its exact numerator and denominator and pass the program's own validation. The official current `Fee::apply` rounds upward; MAIN's local `Fee::apply` comment/implementation describes truncation, so impact must come from deployed-code VM and account deltas, not that local helper. [Official update logic](https://docs.rs/spl-stake-pool/latest/src/spl_stake_pool/state.rs.html), [official `SetFee` processor](https://docs.rs/spl-stake-pool/latest/src/spl_stake_pool/processor.rs.html).

For `DepositSol`, the deployed code reads `sol_deposit_fee` from the pool state and computes a fee in **pool tokens minted**, then splits that fee between manager and referral according to `sol_referral_fee`; recipient pool tokens and manager/referrer credits can change while the SOL input and program ELF remain fixed. Bind the manager fee token account and referral token account actually present in the retained action; do not label all fee tokens “manager fee.” The existing adapter already qualifies the no-SOL-deposit-authority, ten-account `DepositSol` shape. Its summary measures recipient tokens, manager fee tokens, pool supply and reserve lamports from execution accounts; only `pool_tokens_received` is currently promoted as a stable deposit finding subject. Other quantities need exact operation-specific report reconciliation, and any newly promoted subject needs its own semantic proof. `docs/examples/mainnet-stake-pool-record.json` is a retained real deposit record, and `deploy/bundle/corpus/manifest.json` lists one DepositSol and nine WithdrawSol records. Eligibility still must inspect that selected record's complete account boundary, deployed ELF, fee and referral account, and a nonzero mint outcome; the audit does not assert a numeric consequence for a not-yet-run proposal. `docs/examples/mainnet-stake-pool-withdraw-record.json` and the nine withdrawal records cover the separate supported withdrawal action.

For `WithdrawSol`, current fee and future fee are distinct. A real `SetFee(SolWithdrawal)` leaves the active fee unchanged at the retained Clock and schedules a later value, so the same immediate withdrawal is a no-consequence control. Advancing Clock to make it active would change the question and is excluded. Directly replacing active `sol_withdrawal_fee` would be a state counterfactual that **does not model** that admin instruction. The pending value must be decoded and bound if a later withdrawal operation is ever considered. This makes withdrawal a weaker second operation despite strong downstream measurement. `SolReferral` changes the split of an existing deposit fee, not the fee itself; pools with zero deposit fee provide no useful consequence.

## A versus B: proposed-state production

**A, typed account-state derivation.** For Stake Pool, use a pinned compatible official complete `StakePool` Borsh type, decode the observed account, mutate exactly `sol_deposit_fee`, serialize, preserve the fixed account length and trailing bytes, and prove all bytes outside that typed fee representation unchanged. Variable-length options before the fee and stale trailing bytes prohibit fixed offsets or reconstruction from Eplyx's partial reader. A is feasible only after version/roundtrip proof on the retained real pool. It is a direct counterfactual and proves no manager action. For withdrawal A can create an active-fee counterfactual, but that is deliberately different from a real `SetFee` result. Kamino/Meteora/Orca/Drift have no acceptable A with current typed models. Token-2022 pause can use the same official TLV technique as Step 8.

**B, simulated real configuration instruction — selected.** Build the official `SetFee(SolDeposit(proposed Fee))` instruction (or byte-identical instruction validated against the official enum), using the observed pool's manager key as a signer meta. Start a fresh VM from the retained account boundary, same pinned Clock and same deployed Stake Pool ELF, execute the config transaction, retain its message/outcome/logs/post-accounts, and require success. Decode the post-pool state with a complete pinned official type plus MAIN's reader; require exactly the proposed numerator/denominator and semantic equality of every other typed field. Require the pool envelope, account length, all other accounts, and any trailing bytes to remain unchanged; if the program's serialization legitimately changes padding, record and explicitly justify those bytes before admitting the case, never silently ignore them. The post-config pool account becomes only the proposed `DepositSol` pre-state. Neither config transaction fee nor manager account/synthetic payer state enters the downstream comparison. This path is stronger for the variable Borsh layout and models the protocol's own checks. It establishes what an *assumed manager-signed* instruction does inside the VM, not that a real manager can or will sign. [Official instruction builder](https://docs.rs/spl-stake-pool/latest/src/spl_stake_pool/instruction.rs.html), [official processor](https://docs.rs/spl-stake-pool/latest/src/spl_stake_pool/processor.rs.html).

The manager's historical account bytes may be absent from the retained user-action record because `DepositSol` does not use that account. Qualification must first determine whether the existing provider/acquisition path can supply the manager account at the chosen boundary. If it cannot, any minimal simulation-only account envelope must be clearly declared as an assumption and proven irrelevant to `SetFee` except for signer/key identity; it must never be described as observed historical state. A failed manager-account or VM-admission proof is `config_execution_unavailable`, not a cue to mutate arbitrary bytes.

## Acceptance criteria and non-goals

Acceptance requires the closed Token-2022 operation and identity remain unchanged; one distinct new operation/ChangeSpec ID; stale hash/rational/referral/epoch mismatches fail before VM; real `SetFee` success and exact post-config fee with unrelated typed state and account bytes preserved; an explicit manager-signature assumption; same deployed Stake Pool ELF and same retained supported `DepositSol` on both action sides; exact VM/account reconciliation and specific pool-token/fee consequence; equal-fee and rounding/no-consequence controls; a retained real Stake Pool deposit case; offline full reproduction; hosted persistence/read verification/restart; and tamper tests for every provenance boundary. Guided UI is not required.

Non-goals: a third parameter, generic config-field registry, authority changes, proof of manager authorization, governance, monitoring, generic protocol serializer, cross-kind composition, arbitrary protocol onboarding, a new downstream action, new provider, live market prices, TVL estimates and any claim about deposits beyond the retained action.
