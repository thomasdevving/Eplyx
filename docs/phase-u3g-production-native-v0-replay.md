## Experimental evidence versus durable `ReplayRecord`

## Product boundary under review

The smallest plausible schema is an optional native-v0 execution-message field on the existing `ReplayRecord`, plus typed envelope, runtime-context and strict-outcome fields. Absence would retain the legacy JSON shape. V0 loading would reconstruct the signed message and LUT proof from raw account evidence, compare the result to `HistoricalTransaction`, and validate target/dependency identity before execution. Bundle dependency artifacts can continue to be keyed by program ID: T1 and T2 use the same Scope, KLend, ATA and Token-2022 binaries; T2 alone adds Farms, and T1 alone uses legacy SPL Token. U3B.2 measured 28,528 bytes of repeated LUT raw-account bytes across its eight-transaction proof corpus; this two-record case does not justify a new content-addressed store on that measurement alone.

The current product does not yet implement that design. Its executor accepts `Option<solana_message::Message>` and sends `Transaction`, whereas both baselines require `VersionedTransaction::V0`, historical Rent and EpochSchedule, ProgramData-before-header seeding and full CPI comparison. `ReplayRecord::validate()` rejects LUT-backed v0, and the Kamino boundary helper still fixes the token-program owner to legacy SPL Token. Reusing the experimental example as a second product executor would violate the single-architecture requirement. Product eligibility, corpus, bundle and ordinary CI claims therefore remain pending.

## Stage 3/74 architecture gate — progression stopped

An optional message field is compatible with old JSON, but it is **not a sufficient durable replay extension**. Several existing product invariants are built around a legacy transaction and a single inline account vector:

1. `ReplayRecord::message()` reconstructs compiled instructions from normalized account metas and returns a legacy `Message`. `ReplayRecord::validate()` explicitly refuses LUT-backed v0 and invokes the current Kamino contract, which refuses the original Scope and ATA companions. Its `primary_instruction()` chooses the first instruction with the program ID, without a target outer index. The product needs a new execution-message and target model across validation, execution, selection and reporting.
2. `executor::execute_in_environment()` loads each ELF through `add_program`, sets only a reconstructed Clock, seeds the existing accounts, and submits `Transaction`. U3F instead seeds historical ProgramData before executable headers, supplies exact Rent and EpochSchedule, derives Instructions from the complete native v0 transaction, and submits `VersionedTransaction`. Moving only the example runner into CI would leave a second execution stack and would not make the existing replay abstraction correct.
3. `OriginalExecution` stores success, fee, a state hash, limited per-account digests and summarized CPI frames. `ExecutionResult` likewise records summarized CPI calls and present watched accounts only. Strict U3F fidelity requires exact logs, compiled CPI indexes and bytes, return-data representation, presence/absence and full account lifecycle fields. The existing `PostAccountDigest` lacks executable and rent epoch. Both product result and gate contracts need revision; merely storing `matched=true` is forbidden.
4. The two historical seed sets contain **56,408,317 raw account-data bytes**: 22,999,752 for T1 and 33,408,565 for T2. **22,488,554 raw bytes recur identically across both** (chiefly two 10 MiB ProgramData accounts and the Scope ProgramData account). `ReplayRecord.accounts` serializes data as hex, so these seeds alone would require at least 112,816,634 JSON hex characters before field overhead, raw archive provenance and post-state evidence. The current bundle deduplicates `.so` files, but it has no account-evidence object store and cannot share those historical ProgramData images across records. Embedding them in each record would duplicate the same historical executable bytes even after the binary dependency deduplication. Dropping or regenerating the padding would weaken the exact pre-state guarantee U3F proved.

This crosses the brief's explicit **major `ReplayRecord`/bundle evidence-model redesign** stop condition. I stopped before modifying the product schema or executor. No two-record product corpus, Kamino bundle, ordinary `ci check`, hosted check or U3G mutation claim was produced. The existing experimental replays remain valid and separate. A passing U3F example is not a passing product path.

### Architecture revision needed before resuming U3G

Design a common execution input and result interface used by both legacy and native-v0 messages. Keep the legacy reader/serialization stable. Add a versioned account-evidence reference that can carry exact historical pre-state and runtime sysvars inside a bundle, deduplicate identical blobs by hash, and validate every reference when a record is loaded. The record ID must bind message, LUT proof, envelope target, pre-state/evidence identities, runtime context, dependency manifest and baseline. A strict outcome variant must bind full watched post-state and complete CPI/log evidence. Bundle verification must traverse those references offline, and `ci::check` must use the same backend as experimental U3F. This is a design direction for the next phase, not implemented behavior.

Raw LUT evidence can be stored with the same referenced account-evidence mechanism. U3B.2 measured only 28,528 duplicate LUT bytes across eight transactions, so LUT size alone does not justify the store; the measured 22.5 MiB duplicate ProgramData state in this two-record corpus does. The store must retain original account bytes and metadata, with a lossless compact physical form if used. The existing binary dependency manifest should remain the sole program-binary model; native programs such as Compute Budget should remain native.

The mixed-token fix should use the shared U1 `TokenProgram` owner-based decoder and check the owner against validator token-balance program ID, decoded mint and target instruction roles. Changing the Kamino boundary contract to accept either program by name, or trying both decoders on bytes without binding the account owner, would not satisfy the required mismatch tests.

## Current claims and decisions

T1 and T2 are still two faithful **experimental** historical replays. Their U2 deposit/borrow subjects and zero self-findings remain established by U3F. They are not ordinary `ReplayRecord` observations, and no product corpus/bundle/CI/hosted hash, size, timing or result exists for them. No production candidate differential was attempted. T3 Rent acquisition, T4 same-slot interference, wrapped-SOL lifecycle and multi-action attribution remain outside this stopped phase.

**Adapter #4 decision: C — replay architecture needs revision. Adapter Contract v2 decision: C — insufficient product-path evidence.** The next recommended phase is the shared execution/evidence-model revision above, followed by a fresh U3G attempt against the same frozen T1/T2 records and unchanged Stake Pool controls. Do not call the two-record Kamino slice broadly representative.
